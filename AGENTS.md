## 1. Mission & System Overview

**Prakaram** (प्रकारम्) is an ultra-minimal, privacy-first Vedic chanting companion and Prakara studio. It enables practitioners to chant sacred Vedic texts line-by-line, learns their personal reciting cadence (*laya*) using classical prosody (*Chandaḥ-śāstra*), allows compilation of custom ritual sequences (*Prakaras*), and supports real-time synchronized group chanting via serverless WebRTC.

## 1b. Mental Model of the Media

Everything in the library is either a **source** or a **prakaram**. Keep this split when adding content, data fields or UI.

* **Sources are primary things.** The four Vedas (Rigveda, Yajurveda, Samaveda, Atharvaveda) with their samhitas, brahmanas, aranyakas and upanishads (a Taittiriya Upanishad is a source), plus shlokas (the Gita, stotras, smriti and itihasa verses), songs (bhajans, kirtanas, devotional songs) and other primary texts. A source owns its text and its media (swara text, transliteration, translation, audio, commentary). It is an article in the wiki, and its sections are the addressable parts.
* **Prakarams are combinations.** A vrata, an upakarma, a puja, a parayana or any custom sequence is a composition. It owns no source text. It is an ordered list of references to parts of sources (`metadata.parts`, or the items of a prakara), and it shows the referenced text inline. Its own words are only procedure: the sankalpa, instructions and links between parts (vakyas).
* **The four Vedas are ours to fill, from the original Sanskrit.** The Rigveda, Yajurveda (both recensions we care about), Samaveda and Atharvaveda are the primary sources of the library, and we build them ourselves from the original Sanskrit texts (public-domain printed editions and manuscripts, checked against each other), not by copying a typed edition whose licence forbids it. This is a task of its own, separate from the wiki and the player. Until it is done the library holds only a few suktas, some typed from licensed editions that stay `draft` (see `MAINTAINERS.md` §7). Plan for it: addresses and editions first (see below), then fill one Veda at a time.
* **Decompose, never copy.** People take parts out of a source to make something new, so the parts must be addressable and the source stays the single copy. Never paste source text into a composition. A source shows where it is used (Used in); a composition shows where each part comes from.
* **Media belong to sources, compositions inherit.** What a source brings is declared on it (Brings). A composition brings what its parts bring. The player plays text today; other media are declared for later.
* **Where it shows in the code:** `metadata.kind` (`source` by default, `composition`), `metadata.parts`, `metadata.categories` and `metadata.veda` for classification, `metadata.media` for declared media, and `src/services/wiki.ts` for the derived view. A new song or shloka collection is a source with its own categories. A new vrata is a composition. Section 3E has the wiki rules.
* **Vendored source text is compiled into `sources/`, never into the bundle.** Every source we reference live (the Rigveda maṇḍalas, Taittirīya Saṃhitā kāṇḍa 4, the Āraṇyaka prapāṭhakas, the Śrī Sūkta) is generated by `bun run sources:refresh` into `sources/<docId>.json`: the script fetches and parses each upstream (parsing lives in `scripts/sources/`, not in `src/`), attaches `metadata.provenance`, and writes `sources/manifest.json`. The app fetches one file on demand from jsDelivr at a pinned commit (`SOURCES_PIN` in `src/services/vendored.ts`, driven by the `VENDORED_SOURCES` table in `src/data/vendoredSources.ts`); the dev server serves the same path from the repo root. There is no proxy. Every processed file carries `metadata.provenance` (upstream URL, ref, retrieval date, parser, licence, attribution, sha256) and stays `draft` until proofread; `scripts/sources/manifest.test.ts` re-checks the index against the table and the files on disk.

### Core belief: everything belongs to the public

Everything in the Koshah belongs to the public. Our admission rule is under exploration: today we admit only text, translation, commentary, audio and readings that their authors have dedicated to the public domain (CC0), and nobody owns an edition, a reading or a prakaram. Options for admitting attributed open-licence text (CC BY-SA, ODbL, per-layer licences) are being weighed; until the owner decides, nothing new outside CC0 is added. A typed edition that carries rights we cannot clear stays out, or stays `draft` until we replace it with our own text from the original. Provenance (which printed edition or manuscript a text was established from) is recorded so that scholars can check it, and it is never a licence. Contributions that need credit-only licences are not accepted.

### Canonical text, readings and the model going forward (decided, not built)

* Each source has **one canonical text** (`mūla`), established by us from the original Sanskrit and kept in git (git history is its version history). Recensions (`śākhā`) are separate sources: Taittiriya, Kāṇva and Mādhyandina differ in wording and accents.
* A **reading** (`pāṭhāntara`) is a named patch on a source: the mantra address, the position, and the replacement or skip, anchored to the source revision it was made against (marked stale if the source moves). A prakaram kriyā can carry readings. A personal reading stays in the user's prakaram and never alters the source. A reading can be published as a named variant, attributed and not owned, and a widely used variant or a real correction can be promoted into the source by pull request.
* Order of work: (1) the address scheme (`nirdeśa`) with ranges (built, at pada level, with a padya step; see below), (2) kriyās that carry readings in the data model, (3) the editing UI for readings, (4) the contents page per source, (5) audio with per-line timings, (6) songs and shlokas.

### Nirdeśa (the address scheme, built)

A chunk is a **pada** (पाद, one displayed line), not a traditional mantra, and the word "mantra" is overloaded, so the grouping above the pada is a **ṛk** (ऋक्, a verse in metre; shown as "ṛk" in the UI, while the code, the `p<n>` address step and the `padyas()` helper keep the older name "padya"). The finest honest address is section plus pada. Never invent mantra or padya numbers: a padya exists only where the text itself prints its numerals. `src/services/nirdesa.ts` (pure) owns the grammar:

* `<source>` | `<source>/<s>` | `<source>/<s>.<l>` | `<source>/<s>.<from>-<to>` | `<source>/<s1>.<l1>-<s2>.<l2>`. `s` is the section's `sectionNumber`, `l` the 1-based pada inside that section; `from <= to`, and `s.3-3` normalises to `s.3`. A piece id (`docId`, `docId/n`) is already a nirdeśa.
* **Padya step** (only in sections that have a padya level): `<source>/<s>.p<n>` (padya `n`, the number printed at its end), `<s>.p<n>-p<m>`, `<s1>.p<n>-<s2>.p<m>`, `<s>.p<n>.<k>` (the k-th pada inside padya n) and `<s>.p<n>.<a>-<b>`. It always resolves to whole padas, and every older address stays valid. `padyas(section)` (`src/services/padya.ts`) derives the level from the printed numerals (`॥ १ ॥`, `॥ 1 ॥`, any script's digits) at the end of a pada: a numeral ends a padya only when the section has two or more of them (Sri, Purusha, Durga, Narayana). One trailing numeral (the Namakam or Chamakam anuvāka number) is the anuvāka number, not a padya number, and a source with none (Shanti, Ganapati) has no padya level. A numeral not greater than the one before it is not a boundary; gaps stay as printed; padas after the last numeral belong to no padya.
* `resolveNirdesa(addr)` returns the document, the sections, the actual `MantraChunk[]` slice and label parts, or a typed error (`syntax`, `unknown-source`, `unknown-section`, `pada-out-of-range`, `no-padya-level`, `padya-not-found`, `reversed-range`). `padaOf` and `nirdesaOfChunk` give a chunk's address by position, never by parsing the chunk id. `selectionNirdesa` builds the address of a selection, snapping to whole padyas unless refined to padas.
* **Citation in words, not dotted or abbreviated.** `metadata.cite` ('TS 4.5') is gone and nothing displays a dotted number or an abbreviation as a citation. Display the way older texts cite, in the work's own division names with Sanskrit ordinals: `Taittirīya Saṃhitā · caturtha-kāṇḍa · pañcama-prapāṭhaka · prathama-anuvāka`, then `dvitīya-ṛk` or `caturtha-pāda` for a padya or pada. `citeInWords(source, address, script)` (`src/services/cite.ts`) builds it from the optional `metadata.place` (`work` and `divisions`, filled only where certain; the section is the anuvāka), through the single Sanskrit renderer (components use `useCiteInWords` from `Sanskrit.tsx`). A source without `place` shows just its title. Our `§s` numbers appear only as plain words ('§3 padas 3–9', '§3 ṛks 2–4'), never as a traditional number.
* A prakara kriyā carries `PrakaraItem.nirdesa`; the old `sectionId` is read for compatibility and rewritten to `nirdesa` on load (`normalizePrakara` in `koshah.ts`, used by the prakara store and the `#p=` decoder). The My prakaram basket is a list of nirdeśa strings (old `{ pieceId }` baskets migrate).
* Numbering is stable once published (`MAINTAINERS.md` §4a). `nirdesa.test.ts` checks the corpus: unique ids, sections numbered 1..n, no empty section.

## 3. Non-Negotiable Vedic & Linguistic Invariants

When editing or generating Vedic texts and transliteration logic:

### A. Swara Preservation
* **Never strip or replace Vedic cantillation marks**:
  - `U+0951` (॑) : *Svarita* (high pitch)
  - `U+0952` (॒) : *Anudātta* (low pitch)
  - `U+1CDA` (᳚) : *Dīrgha Svarita* (independent long accent)
* Canonical source text in `src/data/*.json` is always stored in **Devanagari with explicit swaras**.

### B. Tamil Script Clustering Order
Standard Tamil lacks separate letters for aspirated consonants ($kh, g, gh$). We use South Indian subscript digits (`U+2081–U+2084`).
* **Correct Unicode Cluster Order**:
  $$\text{[Base Consonant]} + \text{[Matra/Virama]} + \text{[Vedic Accent]} + \text{[Subscript Number]}$$
  Example: `தீ॒₄` (base `த` + matra `ீ` + anudatta `॒` + subscript `₄`).
* **Wrong Order**: Placing subscripts before matras (e.g. `த₄ீ`) breaks OpenType text rendering engines (HarfBuzz/DirectWrite).

### C. Chandaḥ-śāstra Cadence Normalization
Do not calculate cadence using raw word counts. Sanskrit prosody uses *mātrās*:
* **Laghu (ह्रस्व)** = $1\text{ mātrā}$
* **Guru (दीर्घ / संयोगे परे)** = $2\text{ mātrās}$ (long vowel or short vowel followed by conjunct/anusvara/visarga)
* **Pluta (प्लुत)** = $3\text{ mātrās}$
* **Daṇḍa Caesura (`|`)** = $2.0\text{ mātrās}$ pause; **Double Daṇḍa (`||`)** = $3.5\text{ mātrās}$ pause.
* **Half letters are beats of their own:** a consonant with a virama (the first member of a conjunct, or a word-final one) is half a mātrā bare, one mātrā with a swara (svarita or anudātta) and two (a dvimātra) with the double svarita. A full letter with the double svarita is also a dvimātra. The short syllable before a half letter is still long by position. These are `syllabifyVedic` tokens in `src/services/syllabifier.ts`, and the learned pace uses the same totals.
* **End rest:** every pada, and so every padya (it ends on a pada), rests $1\text{ mātrā}$ at its end (`END_REST` in `src/services/syllabifier.ts`). A printed daṇḍa or double daṇḍa already is that rest and is longer, so it replaces the rest: pauses never stack. A pada's total is its syllables plus this rest, and the learned pace uses the same total.

### D. Line Kinds and Display Rules
* A line is **swara** if its Devanagari source contains U+0951, U+0952 or U+1CDA (`src/services/swara.ts`). Detect swara on the source, never on transliterated output.
* A **shloka** is a custom verse ending in `॥`; a **vakya** is other procedural text. Sukta lines are **mantras**.
* Titles are shown by Sanskrit akshara count (`src/services/aksharas.ts`), never by UTF-16 length. The header limit is the longest default title.
* Titles and Sanskrit labels follow the selected script; English text does not change.
* Mantra text is ink. Swara syllables use `--swara-up` (purple), `--swara-down` (blue) and `--swara-double` (red) as direct colours, not tints.
* Timing counts only chant: Devanagari letters, marks, swara and dandas (`src/services/syllabifier.ts`). Latin text, brackets, pipes and verse numbers add no mātrās. `ꣳ` is one mātrā of its own.
* Every render and screenshot shows at least one highlighted (active) line. If the active line has scrolled off screen, scroll back to it before capturing.
* **One Sanskrit renderer.** Sanskrit text and titles become visible only through `src/components/Sanskrit.tsx` (`Sanskrit`, `SanskritTitle`, `ArticleTitle`, `ArticleSubtitle`, and the hooks `useScript`, `useSanskritText`, `useTitleText`). They read the selected script from the settings store, so a script change re-renders everywhere, and verse numerals are transliterated per script (Arabic digits in Tamil and IAST). Components must not call `transliterateVedic` or `renderVedic`, or read `title.sanskrit`, directly. `src/components/sanskritGuard.test.ts` fails the build if one does.
* Cadence phases (`off`, `manual`, `waiting`, `measuring`, `engaged`) change only through `transition()` in `src/services/cadenceMachine.ts`, applied by the cadence store. Auto-advance runs in `manual` and `engaged`, unless paused. Auto (cadence) is off by default (`INITIAL_LEARNING` is `off`); saved settings are kept. Do not set `phase` by hand. The transition table is in `DESIGN.md` §5b.

### E. Koshah Wiki

* The wiki is derived from `src/data` on each render (`src/services/wiki.ts`); nothing is stored. Routes are hash routes parsed in `src/services/wikiNav.ts`: `#/wiki`, `#/wiki/<id>`, `#/wiki/<id>/<n>`, `#/wiki/<id>/<s>.<from>-<to>` or `#/wiki/<id>/<s>.p<n>` (a nirdeśa), `#/wiki/Category:<name>`, `#/wiki/Special:Search?q=`, `Special:Random`, `Special:Compose`. Old `#k=` links redirect.
* A **source** owns text and its sections are the addressable parts (`docId/n`); a nirdeśa also addresses padas, padyas and ranges of them. A **composition** (`metadata.kind: 'composition'`, `metadata.parts`) owns no text and references parts. The default prakaras are derived as compositions. Do not copy text into a composition.
* Media are declared per article: text, transliteration and translation are derived; declare only audio, commentary, images or extras in `metadata.media`. The player plays text only.
* The action word is **Follow** (the cadence follows the reader), not "Chant". Each pada has a quiet number (section-relative); where a padya level exists the padya number sits beside the padya's last pada. The player shows the same structure: a quiet ṛk number above the first line of each verse (only where a verse level exists) and an `anuvāka N` heading at the start of each section in a multi-section source (`MantraChunk.section` and `.padya`, set in `getFlattenedChunks`). Tapping two numbers selects a range that snaps to whole padyas, with a `padas` toggle in the range row to refine to padas; the row reads `Follow ṛks 3–5` / `Follow padas 3–9`, Add to my prakaram, Copy link and clear. The article's own play button is the Phosphor `play` icon.
* **My prakaram** is `useBasketStore` (`prakaram-basket`, persisted, validated on load). Items are nirdeśa strings (a section, padya or pada range keeps its address into the prakara kriyā), with optional kriyā names by address (`names`). Following a composition saves it as a prakara first, so it re-saves each time.
* Wiki pages use the player's header (`WikiTopBar`), tokens and gutters, and obey `DESIGN.md` §7b. Layout and anatomy are in `DESIGN.md` §5f.

## 5. Adding New Suktams to the Corpus

When adding a new Suktam from *Saswara Veda Mantrah*:
1. Create a new JSON file in `src/data/<suktamId>.json` matching `MantraDocument` type.
2. Ensure every chunk includes authentic Devanagari with swara marks. Translations may be kept in the data but are not displayed.
3. Register the file in `src/data/index.ts` under `ALL_SUKTAMS`.
4. Add its file name to `SUKTA_FILE` in `src/data/index.ts` (the wiki's edit and history links use it). Optionally add it as an item in a default Prakara preset in `src/data/defaultPrakaras.ts`; that preset then appears as a composition.
5. Set `metadata.veda`, `deity`, `categories`, `summary`, `related` and `usage` (the wiki reads them), and `metadata.status` and `metadata.license` as in MAINTAINERS.md §4a. Status is `draft` until proofread, and text with unconfirmed permission stays `draft`.
6. Run `bun run build` to verify type safety.

## 6. Phase 2 Roadmap: Panchangam & Dynamic Sankalpam

Agents tasked with Phase 2 should implement:
1. Client-side ephemeris (Lahiri / Drik astronomical computation) based on browser geolocation or manual date picker.
2. Derivation of: *Samvatsara, Ayana, Ritu, Masa, Paksha, Tithi, Vasara, Nakshatra, Yoga, Karana*.
3. Dynamic template interpolation for family *Gotra*, *Nakshatra*, *Rasi*, *Sharma/Varma*, and local *Kshetra* (river/temple/city).
